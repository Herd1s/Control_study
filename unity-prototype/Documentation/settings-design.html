ControlLab 设置界面实施规划

2026-11-22 · 设计草案与实施范围 · Unity 作为后续唯一主线

本页是规划交付。上方设置预览可以点击，但尚未改动 Unity 生产界面，也没有接入真实更新服务。更新按钮显示的是明确标注的演示结果。

1. 页面与默认行为

设置采用固定的三类导航：学习、我的小车、软件更新；关于置于侧栏底部。800×600 与 1366×768 中，设置预览完整显示，不依赖滚动。每页只放当前有用的操作，不添加尚未接通的占位开关。

页面首批内容默认行为
学习下次继续上次进度、当前学习位置默认开启；关闭只改变启动入口，已有学习记录与外观保留。
我的小车外观预览、名字、编辑外观复用现有照片与涂鸦编辑器；课程中编辑后返回原位置。
软件更新当前版本、检查更新、更新说明、下载与安装状态首版手动检查、下载和安装。打开设置不自动联网，不打断实验。
关于版本、项目链接、本地资料说明不用学生填写仓库地址、登录 GitHub 或输入访问令牌。

沿用白、灰、蓝和圆角按钮。正文与说明不小于 17 px；分类切换使用短淡入，尊重系统“减少动态效果”偏好。开关即时保存，不再添加一个全局“保存设置”步骤。正式软件打开设置时暂停实验，关闭后恢复，并拦截背景鼠标与键盘操作。

2. 启动偏好与学习记录分开

现有 Unity 实现将 rememberProgress 和页面位置放在 LearningProgress 中，关闭开关会保存 hasProgress=false。随着课程增加，这个语义应调整为“是否自动继续”，而不是删除历史记录。

  • AppPreferencesStore 保存启动偏好和未来明确需要的应用设置。
  • LearningProgressStore 保存章节、页面、讲解主题及展开状态。以后按课程实际实现增加稳定的 lessonId、stepId，不保存不存在的课程入口。
  • CartProfileStore 继续保存名字、颜色、照片与涂鸦，关闭自动继续不影响这些资料。
  • 迁移读取现有偏好与进度，保持原来的开关值；新增独立偏好文件后记录版本，写入前备份，迁移失败保留原数据。
  • 返回第一章时，小车居中、杆竖直静止，等待学员操作；不恢复上次退出时的速度、跌倒或拖动状态。

页面、主题和设置改变时保存进度；正常退出、窗口失焦时保存装扮草稿。未来 Python 作业与代码另设自动保存，不应因为关闭“下次继续”而停止保存。当前 Unity 尚未迁移后续 Python 课程，不提前显示虚构的完成百分比。

3. 更换皮肤不改变学习位置

现有 ShowStudio() 会重置实验并把保存页面改为 Studio，完成后固定进入入场动画。设置中的“编辑外观”需要区分两种进入方式：

模式完成按钮完成后
Onboarding 首次创建完成，进入第一章小车从左侧驶到中央，再开始第一章。
Customize 中途修改保存并返回保存外观，返回原课程与讲解位置，不再次播放入场。

CartStudio 接收进入模式和返回位置。编辑期间不覆盖原课程检查点；正常退出时保存新外观，下次仍依据启动偏好进入原课程或首页。照片与涂鸦继续分层，移除照片不会清除绘画。

本 HTML 仅演示名字与六种颜色，编辑入口尚未连接 Unity。正式实现复用已有照片选择器、笔刷、橡皮和撤销，不建立第二套绘画工具。是否支持“放弃修改”需与草稿自动保存一致：若提供取消，进入中途编辑时先记录外观快照，取消明确恢复该快照。

4. GitHub 更新流程

界面使用“软件更新”作为学生入口；GitHub 是分发来源。当前 Unity 原型版本为 0.1.0；清理前核验的旧 Python/Qt 代码版本为 0.2.4。既有旧发布工作流构建的是 Python 产品，不能把旧安装包当作 Unity 更新。

  1. 用户点击检查更新，后台读取发布信息，不冻结设置窗口。
  2. 只选择符合本产品与平台的正式版本；显示版本、简短说明和下载大小。
  3. 用户点击下载，显示进度与取消；临时文件完整下载后核对大小和 SHA256。
  4. 校验通过后显示“安装并重新打开”；用户点击后先完成学习资料保存，失败则留在软件内说明。
  5. 由独立安装器在 Unity 退出后执行替换，避免覆盖正在运行的文件。安装结束启动新版，新版读取原用户资料并恢复学习位置。
  6. 只有安装完成记录与新版首次启动核对通过，才显示更新完成；启动安装器不等于升级成功。

发布身份与安装边界

  • Unity 建议使用 productId=controllab-unity、platform=windows-x64、独立 unity-vX.Y.Z 标签与 ControlLab-Unity-Setup-X.Y.Z.exe 资产。发布清单包含版本、资产名、大小和 SHA256。
  • 客户端核对产品、平台、版本、资产来源与校验值；草稿和预发布版本不向普通学生推送。不能简单把整个仓库的最新 Release 当成当前产品的更新。
  • 旧 Python 客户端目前使用全仓库 releases/latest。在统一发布渠道前，应明确 Unity 专用更新清单，并处理旧客户端对最新版本的读取，防止混用；删除本地旧版不自动迁移远端发布。
  • 安装器使用稳定的产品安装身份和目录；程序文件与用户资料分开。更新、卸载和版本迁移不能顺带清空学习资料。
  • HTTPS 与 SHA256 校验文件传输和内容一致性，不等同发布者数字签名。正式分发前单独确定 Windows 签名方案，未签名时不得声称已签名。

用户能理解的状态

状态界面表达
尚未检查显示当前版本与“检查更新”。
已经最新成功读取并筛选后，确认没有更高的匹配版本。
暂无匹配发布已成功读取发布信息，但没有当前 Unity 平台的正式安装包；当前原型仍可使用。
404 / 不可访问“暂时无法读取发布信息，请稍后重试或查看项目。”不能仅凭 404 武断认定没有发布。
网络中断 / 超时 / 限流明确说明连接暂不可用，提供重试；保留现有软件和学习数据。
文件不完整 / 校验失败停止安装并允许重新下载，不把错误当作成功。
取消下载回到可下载状态，不影响已经安装的版本。
安装未完成保留日志与已验证安装包，提供重试；实际回滚能力需由安装器方案验证。

本草案的“检查更新”不会发出网络请求；它只演示“尚无 Unity 正式安装包”这一状态，不代表 GitHub 仓库当前情况。

6. 三阶段交付与验收

第一阶段 · 统一设置与外观入口

将三个分区接入 Unity，复用现有保存能力；实现首次创建和中途修改的不同返回流程。更新页先准确说明尚未接入的能力，不放置看似可安装的假按钮。

验收：两种窗口尺寸无需滚动；设置屏蔽背景操作；关闭后继续原实验；中途修改皮肤返回原课程；正常退出及重启保留外观与讲解；开关变化即时保存。

第二阶段 · 数据分离与真实更新发现

拆分偏好与学习记录，完成旧格式迁移；实现 Unity 专用发布信息读取和状态展示，提供经过产品筛选的真实版本说明。

验收：关闭自动继续不丢课程记录；迁移和损坏回退不破坏原文件；没有匹配发布、404、超时、限流与已有最新版本分别显示；旧 Python 资产不会被选择；操作取消与界面关闭后没有悬挂任务。

第三阶段 · 安装包与软件内升级

建立 Unity Windows 安装器和发布清单，完成下载校验、退出交接、安装与重启；发布前生成候选产物并验收。

验收：在干净 Windows 环境测试首次安装、覆盖升级、取消、文件校验失败、安装中断、重启恢复与资料保留。分别记录本地测试、GitHub 构建、发布资产与真实安装结果，不能互相替代。

7. 旧版清理范围

用户已明确选择：删除整个本地旧版工程，仅保留 Unity 工程。Unity 因此成为后续唯一主线，工具与说明也应解除对旧 Python 工程、其虚拟环境和发布脚本的依赖。删除与独立化由本次工程整理任务执行；此设计文件自身不会删除文件。

这一授权针对本地旧版工程。远端 GitHub Release、标签与发布资产不随本地清理而删除；建立 Unity 新发布通道时仍需隔离旧产品资产。操作系统用户目录中的学习资料与本地工程目录分别核对，避免把工程清理误当成清除个人资料。
